# Survey: load-adaptive worker count for CPU-bound batch jobs on shared Linux servers (no sudo)

Date: 2026-10-27. Need: one pool over ~1M items; every 30–60 s read machine load (other users / idle CPU / loadavg) and set how many workers may pull items next interval; floor 2, ceiling N.

Facts verified on the lab server where this survey ran (Ubuntu 24.04.5, systemd 255, 80 cores, cgroup v2, no sudo):
- `cgroup.controllers` of `user-$UID.slice` and `user@$UID.service` = `cpu memory pids` → the CPU controller IS delegated to the user manager (systemd ships `Delegate=pids memory cpu` in `user@.service.in`).
- `systemd-run --user --scope -p CPUQuota=100% true` → rc 0. On a running scope, `systemctl --user set-property --runtime <unit>.scope CPUQuota=250%` changed `cpu.max` from `100000 100000` to `250000 100000` live (tested with a 4 s `sleep`).
- `chrt -i 0 true` (SCHED_IDLE) → rc 0 without root.
- Installed: GNU parallel 20231122, niceload, cpulimit (Ubuntu 0.2 build, has `-m/--monitor-forks`), chrt, taskset. Not installed: ts/tsp, pueue, nq, xjobs (would need a user-local build).
- Other 7 lab servers: controller delegation NOT checked (未查證); re-run `cat /sys/fs/cgroup/user.slice/user-$(id -u).slice/cgroup.controllers` on each.

Stars / last push / license below come from the GitHub API on 2026-10-27 unless marked otherwise.

## Pessimistic recommendation (top 3, with the exact control loop)

None of the twenty does "sample other users' load every 30–60 s and set the active worker count between 2 and N" out of the box; the choice is which 20–40-line loop to write and what it drives. (1) **systemd-run CPUQuota + set-property** is the least code and the only option that gives the admin a kernel-enforced cap he can read in `/sys/fs/cgroup`: start the job as `systemd-run --user --scope -u legal-batch -p CPUQuota=200% -p Nice=19 python run.py` with a plain `Pool(N)` inside, and run a sidecar every 30 s that reads `/proc/stat` twice (or `os.getloadavg()[0]`), computes `k = clamp(2, N, idle_cores_excluding_us − margin)`, and calls `systemctl --user set-property --runtime legal-batch.scope CPUQuota=$((k*100))%` (verified working on this server; verify delegation on the other seven first). Downsides: N processes stay resident and get time-sliced over k cores, so memory is N× and `top` still lists N processes, which some admins read as hogging even when the cgroup says 2 cores; also if the signal does not subtract your own CPU it oscillates. (2) **DIY in-flight window over stdlib Pool** is what the admin literally asked for: `Pool(N)` + `imap_unordered` fed by a generator that acquires a resizable semaphore before yielding each item; a thread resizes the window to k every 30–60 s (to shrink, it acquires permits itself; to grow, it releases). Idle workers cost nothing, so only k items are being computed at any time, and the reaction time equals one item's runtime. Downsides: no library to blame, semaphore-resize bugs are yours, and the load signal must be "other users' CPU" (sum `pcpu` of processes whose user is not you, or /proc/stat idle minus your own workers' utime deltas) rather than raw loadavg, otherwise your own workers push the count down. loky's `_resize` is not a shortcut: it blocks until the pending queue drains. (3) **GNU parallel with `-j procfile` + `--limit`** only if you are willing to restructure the job into ~1–2k chunk files run as `parallel -j ~/jobs.txt --limit ~/other-users-busy.sh --nice 19 python worker.py {} ::: chunks/*`, with the same sidecar writing k into `~/jobs.txt` (re-read at every job completion) and `other-users-busy.sh` returning 1 while the machine is busy; `--load 70%` is a cruder substitute that counts machine-wide running processes including your own. Downsides: every chunk re-imports Python and reloads the BM25 index/regex state, a running chunk cannot be shrunk so chunk length bounds the reaction time, and the stdout/stderr plumbing of 2k jobs is one more thing to debug. Skip cpulimit (duty-cycling, dormant), pueue/ts (no load sensing, not installed, same chunking cost as parallel), dask Adaptive (queue-driven, would need a subclass anyway) and all the PyPI "resource-aware pools" (dead or zero-adoption). SCHED_IDLE/nice 19 is free and should be added to whichever option wins, but on its own it changes nothing the admin can see.
